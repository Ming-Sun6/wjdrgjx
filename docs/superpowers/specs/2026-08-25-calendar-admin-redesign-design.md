# 活动日历管理重设计规格

## 目标

重做活动日历管理页，使管理员能按自然顺序创建、理解和复用日程，同时保留现有分类、普通日程、跨日日程、循环日程、组合甘特图、每日清单、复制、启停和删除能力。

## 交互模型

管理页不再把“单日、连续、定期、组合”并列为四种互斥类型，而是拆成两个维度：

1. 日程结构：普通日程或组合日程。普通日程的日期方式可以是连续时段或指定多个不连续日期。
2. 是否重复：所有结构都可以开启或关闭重复。

日期统一填写“开始日期”和“单次持续天数”。页面实时显示本次结束日期。持续 1 天等同原单日日程，持续多天等同原连续日程；开启重复后，每次 occurrence 都保持相同持续天数。

旧版 `date-list` 使用“指定日期”方式编辑：管理员通过大尺寸日期控件逐个加入日期，并以可删除的日期标签显示。不连续日期保持原始间隔，不会被转成连续跨度。指定日期模式不支持重复；切换到重复前必须先改为连续时段。

## 页面布局

页面按以下顺序组织：

1. 顶部说明和快速操作。
2. 活动分类折叠区，保留新增、改名、调色、排序和停用。
3. 日程编辑器：
   - 基础信息：名称、分类、普通/组合、状态。
   - 日期与时间：连续时段/指定日期切换、大尺寸日期控件、今天/明天/下周快捷按钮、日期标签、单次持续天数、计算后的结束日期、可选起止时间。
   - 重复设置：开启开关、单位、间隔、星期/月日、结束方式。
   - 展示与说明：跟随分类颜色、常用淡暖色调色板、自定义颜色与十六进制色值、描述。
   - 组合内容：甘特任务块/每日清单和子任务，仅组合日程显示。每个子任务继续支持全时段、相对连续日期、指定偏移、子任务循环、启停、重点标记、起止时间、颜色、说明和排序。
4. 右侧预设区：预设名称、保存当前配置、套用、删除。
5. 已配置日程列表：筛选、编辑、复制、启停和删除。

桌面端编辑器与预设区双栏显示；窄屏改为单栏。页面使用现有后台变量和视觉风格，不引入新框架。

日期选择区域扩大可点击范围，并提供明确的日期预览，避免只依赖浏览器较小的原生日历图标。颜色选择以可点击色块为主，自定义颜色控件和色值输入为补充；选择色块、颜色控件或色值时三者保持同步。

## 数据兼容

数据库继续使用现有 `schedule_type`：

- 普通、不重复、持续 1 天：`single`
- 普通、不重复、持续多天：`continuous`
- 普通、开启重复：`recurring`
- 组合日程：`composite`，是否重复由 recurrence 字段决定
- 普通、指定多个不连续日期：`date-list`，使用 `legacyDates` 保存日期且不可开启重复

读取旧数据时，原 `single`、`continuous`、`recurring`、`composite` 和 `date-list` 都转换成新编辑器状态。结束日期与开始日期的差值转换成持续天数，因此旧循环日程也能编辑为多日持续。`date-list` 的 `legacyDates` 原样回填为日期标签；编辑、复制、预设套用和再次保存均保持不连续日期。公共展开逻辑按每个指定日期分别生成一天的 occurrence。

领域层放宽重复规则：只要请求包含有效 recurrence 字段，普通连续时段或组合日程都能重复；旧请求仍保持兼容。指定日期模式拒绝 recurrence。

## 服务器预设

预设存放在 `site_settings` 的 `calendar_schedule_presets` 键中，不增加独立数据库表。最多保存 50 个预设。

接口：

- `GET /api/admin/calendar/presets`：返回全部预设。
- `POST /api/admin/calendar/presets`：保存 `{ name, payload }`。
- `POST /api/admin/calendar/presets/:id/delete`：删除预设。

预设对象形状为 `{ id, name, payload, createdAt, updatedAt }`。ID 使用 `preset_` 加 16 字节随机十六进制字符串；名称去除首尾空格后长度为 1–40，同名比较不区分大小写并返回 `409 PRESET_NAME_EXISTS`。GET 返回 `{ presets }`，按 `updatedAt` 倒序；创建成功返回 `201 { preset }`；删除成功返回 `{ ok:true }`，不存在返回 `404 NOT_FOUND`。达到 50 个时返回 `409 PRESET_LIMIT`，且不覆盖原设置。损坏或非数组的已存设置恢复为空数组并记录错误。

预设创建和删除通过模块内共享的 Promise 串行队列执行完整的“读取、校验、修改、写回”，同一 Node 服务进程内不会发生两个管理员同时读取旧数组后相互覆盖的问题，数量限制也在锁内检查。队列在操作失败后仍继续服务后续请求。并发回归测试会同时发起两个创建/删除操作，验证最终数组包含全部成功变更且不超过 50 项。

预设 payload 使用与日程保存相同的规范结构并经过服务端校验。预设保存名称、分类、结构、持续时间、时间、颜色、描述、循环规则、不连续日期和组合子任务。保存时分类必须存在且已启用，否则分别返回 `BAD_CATEGORY` 或 `CATEGORY_DISABLED`。预设会剥离父日程 ID、legacy ID、所有组合子任务 ID、创建人和时间等服务端身份字段。套用时连续/组合日程的开始日期改成当天，结束日期按持续天数重算；指定日期预设按最早日期与今天的差值整体平移，保留日期间隔。若套用时分类已删除或停用，页面保留其他内容并要求重新选择有效分类。

## 错误处理

- 页面在字段附近显示解释性提示，不依赖隐藏控件的浏览器原生校验。
- 无效时长、循环规则或组合子任务会在发送请求前阻止保存。
- 服务端再次校验全部 payload。
- 预设接口要求管理员登录，失败时不清空现有编辑内容。
- 所有修改请求使用 POST 兼容线上 CDN，已有 PATCH 路由继续保留。

服务端约束如下：日程名称 1–120 字，说明最多 2000 字；持续天数 1–366；时间必须为 `HH:mm`，同时填写时结束时间必须晚于开始时间；循环间隔 1–365，次数 1–500，截止日期不得早于首次开始日期。截止日期约束 occurrence 的开始日期，允许最后一次 occurrence 的结束日期晚于截止日期。组合子任务最多 100 个，名称 1–120 字、说明最多 1000 字；相对偏移、指定偏移、子任务持续天数和子循环必须落在父日程单次持续范围内。指定日期最多 366 个且必须唯一有效。

## 测试与验收

- 领域测试覆盖普通多日循环和组合循环。
- 路由测试覆盖预设读取、保存、限制、删除和权限。
- 管理页测试覆盖新布局、通用重复开关、持续天数、预设操作、旧数据回填及无隐藏必填控件。
- 日历展开测试确认每个循环 occurrence 保持配置的持续天数。
- 回归测试覆盖 `date-list` 的编辑/复制/保存/预设平移，确保日期间隔不丢失。
- 组合子任务 round-trip 测试覆盖四种日期模式以及启停、重点、时间、颜色、说明和排序字段。
- 完成后运行全部日历、后台工具管理、品牌提示和相关回归测试，并执行语法检查与 `git diff --check`。
